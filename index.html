Gemini の方言・アクセント制御

観察: [Osaka dialect] のようなタグを付けても、台詞が標準語のままの場合、アクセントは切り替わりませんでした。台詞自体を方言で書き起こした上でタグを併用すると、標準語読みとは明確に異なる抑揚・雰囲気で読み上げられます。ここから、タグは音素レベルの変換を行っているのではなく、テキストをモデルがどう読み上げるかの解釈ヒントとして機能している、と理解しています。

大阪弁 + tagこの店、ほんま美味いわ。行ってみよか。[Osaka dialect]
大阪弁 tag無しこの店、ほんま美味いわ。行ってみよか。—
博多弁 + tagこの店、うまかねー。行ってみようや。[Hakata dialect]
博多弁 tag無しこの店、うまかねー。行ってみようや。—

Grok TTS（Eve）に同じ大阪弁テキストを投げた結果

聴きどころ: 同じ大阪弁テキストを、タグ併用の有無を変えながら Grok TTS（Eve）に投げた 6 ケースを並べています。テキストに含まれる大阪弁語彙が、音声としてどの程度「大阪弁らしい抑揚・アクセント・リズム」で読み上げられるかを聴き比べてみてください。筆者の主観では、Grok TTS（Eve）はテキストとしては語彙をそのまま読み上げるものの、大阪弁としての抑揚・アクセント・リズムはほぼ再現されず、全体として標準語寄りのイントネーションに聴こえました。[Osaka dialect] や <dialect:osaka> のようなタグを併用しても、音声側に明確な変化は現れません（タグの記号自体を発音してしまう挙動も観測されず、タグが「無視されている」に近い印象です）。公式 docs 上でも、Grok TTS 側に日本語内部の地域アクセント制御を目的とした機能の記載は、確認した範囲では見当たりませんでした。

Grok TTS 側の 06（大阪弁の長文）とまったく同じテキストに [Osaka dialect] タグを付けて Gemini Laomedeia に投げた音源を、対照サンプルとして並べておきます。

聴きどころ: まったく同じ大阪弁長文を、Grok TTS と Gemini Laomedeia の両方に投げた音源を並べています。語尾の上がり方、間合い、語のリズムが両者でどう異なるかを聴き比べてみてください。筆者の主観では、Gemini Laomedeia 側は同じ大阪弁テキストを自然な声で読み上げており、関西圏の話者としての違和感が少ない仕上がりに聴こえました。同一テキストを両 TTS に投げた時点で、日本語内部の方言・アクセント制御の差が、聴感上はっきりと出る結果となりました。現時点では、日本語の方言制御という観点で、Gemini 側に明確な優位性がある、と言えそうです。

長尺サンプル：ナレーションとドラマ

ここまでの短文・probe ベースの検証に対して、長尺で通して聴いたときの印象は別の次元で差が出ます。参考として、約1分のナレーション（「街の朝」）と、感情タグを厚く織り込んだ約1分のドラマ（「二十年後の返事」）の2本を、両 TTS で並べて置いておきます。

NARRATION

「街の朝」——約1分のナレーション（両者1-shot、tag最小）

検証条件: [pause] のみ使用、感情タグや自然言語キャプションによる演出は加えていません。同一原稿を両 TTS に入力し、純粋な原稿読み上げの質感を比較しています。Gemini 側は、約1分の 1-shot 生成が完走しました。

Grok TTS（Eve）— 1-shot・約52秒、冒頭に [breath][pause] を入れた warm-up 版
[breath] [pause] 街の朝は、信号機の色と、駅に向かう人の流れで始まる。[pause] コーヒースタンドに、湯気が立つ。新聞の見出しが、地下鉄の入り口で風に揺れる。[pause] 誰もが、それぞれの一日を、持っている。[pause] 電車の窓に、朝日が反射する。鞄の中には、会議の資料と、昨日買った本。スマートフォンに、通知がいくつか。[pause] 人生とは、こうした小さな積み重ねで、できているのかもしれない。[pause] 歩き出す。一歩、また一歩。[pause] 交差点で信号が変わるのを待ちながら、空を見上げる。雲が、ゆっくりと流れていく。[pause] 今日という日も、きっと、悪くない。

「二十年後の返事」——感情タグを厚く重ねた約1分のドラマ

検証のねらい: 約1分の一人称ドラマ原稿（雨の日、二十年封を切らなかった手紙を開ける場面を語る独白）に、悲しみ・囁き・息遣い・笑い・溜息といった感情タグを意図的に厚く織り込んだ原稿を用意しました。長尺と感情表現が重なったとき、両 TTS がそれぞれどのような声の連続性・情感の推移を再現するかを聴き比べてみてください。

生成条件: Grok TTS（Eve）側は原稿を 1-shot で通して読み上げています。Gemini 側は同じ原稿をそのまま投げると途中の chunk で filter が発動する場面があり、5つの chunk に分割して生成し、通らなかった chunk については感情タグを外した plain テキストに落とし、タグ付きで通った chunk と繋ぎ合わせています。

Gemini Laomedeia（5チャンク連結・約45秒）
● chunk-01（tag付き OK）: [breath] ……雨が、降り始めたわ。 [pause] 古い机の、一番下の引き出し。[curious] 指が、紙の端に触れた。 ○ chunk-02（原文ブロック → plain + 文言変更で通った）: これは、夏の手紙。まだ開けられていない。 ○ chunk-03（原文ブロック → plain で通った）: 便箋を開くと、インクの匂いがした。文字で、「あの時は、ありがとう」と、書いてある。ふふ。 ◎ chunk-04（リトライ複数回の後、tag付きで 1-shot 成功）: [chuckle] そうだった。私、あの時、何も言えずに別れたんだった。[whispers] ごめんね。返事が、二十年、遅れました。 ● chunk-05（tag付き OK）: [pause][breath] さあ。[mischievously] 今度は、私から書こうか。[excited] 便箋を、新しく、用意しよう。
生成時の記録: 原稿を一括で投入した場合、Gemini 側は FinishReason.OTHER を返して空応答になりました。そこで原稿を 5 つの chunk に分割して生成しています。一部の chunk は感情タグ付きで生成が通らず、chunk-02 と chunk-03 は感情タグを外した plain テキストに落として生成、chunk-04 はリトライの結果タグ付きで 1-shot 生成が通った音源を採用しています。

※2026-05-11 再検証: 本来意図したタグ盛り全文原稿（Grok 1-shot 原稿を Gemini 自然言語タグに置換した版、[trembling] / [whispers] / [excited] 等を使用）を 1-shot で投入したところ、Gemini 側は依然として FinishReason.OTHER を返し、audio は破棄されました。chunk 分割と一部 plain 化が現時点でも不可避である挙動が裏付けられています。
聴きどころ: 感情が動く数箇所で、声色がどう揺れるかを聴き比べてみてください。たとえば「今度は、私から書こうか」（いたずらっぽく）、「ごめんね」（囁くように）、「あの年の、夏の手紙」（息を呑むように）。Gemini 側では [mischievously] [whispers] [gasp] といった自然言語寄りのタグが、Grok TTS 側では <whisper> <sad> といった構造化タグが、同じ物語のなかでどのように異なる表情に落ちるか、というのが比較の観点です。

現時点での筆者の印象: Gemini Laomedeia については、感情表現を厚く織り込んだ長尺の読み上げは、現状では難しい場面があるという印象を持ちました。一方で、短文〜中程度の長さで、解説やナレーションを淡々と読ませる用途であれば、十分に実用的な質感が得られています。いずれも 2026 年 4 月時点・preview モデルでの感触であり、今後の正式リリース・アップデートで改善されていくことを願います。

公式 docs 上で確認できなかった点と、運用上の補足

  • [softly] タグと同義語タグの挙動: 2026-04-19 の 中立短文での filter-probe 検証では、同じ意味域の [quiet] / [hushed] / [muted] / [gently] / [calm] が通過する一方、[softly] だけが単独でも一貫してブロックされる挙動が観測されました。2026-05-10 の再検証では、[softly] も中立短文では通る一方、感情負荷や声に関するメタ表現を含むテキストでは FinishReason.OTHER が返り、audio が破棄される場面がありました。さらに 2026-05-11 の再検証では、[calm] / [gentle] も中立短文なら通過するものの、slow/soft 文脈では PROHIBITED_CONTENT でブロックされることを確認しました。つまり、柔らかい声を指示する同義語タグは迂回策になり得ますが、テキスト負荷が高い文では同義語側も個別確認が必要です。
  • Gemini の長尺・感情タグ重畳時の失敗: 公式 docs に記載された token 上限（入力 8,192 / 出力 16,384）に達する前に失敗するケースが大半で、トークン上限ではなく safety filter 側の挙動に起因する失敗、と理解しています。chunk 単位では通る文字列でも一括投入で空応答になる場合があり、応答は完全には決定的ではありません。
  • Grok TTS の長文冒頭 warm-up: 原稿先頭に [breath] を挿入すると、冒頭トークンの初読不安定性は再現しないレベルまで緩和されます。[pause] 単独では同等の効果が認められなかったことから、呼吸音の音響的な手がかりが冒頭トークンの読みを安定させる役割を果たしている可能性がある、と現在は解釈しています。今後のモデルアップデートで改善されていくことを願います。
  • API エラーハンドリングの設計上の含意: Gemini は HTTP 200 を返しつつ失敗が通知される設計のため、SDK 側で finish_reason / block_reason / 空 candidates を総合判定する handling を最初から組んでおくのが無難です。HTTP ステータスだけに依存すると取りこぼします。Grok TTS 側は HTTP ステータスで成功・失敗が切り分けられます。
  • Gemini 側 voice descriptor の非保証: descriptor（Smooth / Mature / Bright 等）は話者の性別を保証する指標とはなっていませんでした。実際、Sadaltager（Knowledgeable）と Algieba（Smooth）は男声として、Despina（Smooth）・Gacrux（Mature）・Aoede（Breezy）・Laomedeia（Upbeat）は女声として音声が生成されています（descriptor 自体に性別属性が含まれているわけではなく、生成された音声の聴感上の性別分類です）。30 voice から voice を選ぶ際は、descriptor で当たりをつけ、短い 1 行を試聴して確認する 2 段の工程が実務上はほぼ必須です。
  • 今回の検証で発生した API 利用料（実績）: 2026-04-19 〜 2026-04-20 の約2時間の検証で、両サービスを合わせた利用料の総額は $0.25 未満でした。内訳の概算は、Gemini 3.1 Flash TTS が $0.10 〜 $0.15（成功音声 約60本 + 失敗リクエスト 約30回を含む）、Grok TTS が $0.01 未満（音声 約20本、検証時の Beta 価格 $4.20 / 1M characters からの試算。2026-05-11 12:00 PM PT 以降は GA 移行で $15.00 / 1M characters へ）。失敗リクエスト時の課金挙動については両サービスとも公式 docs 上での明示的な記載を確認できておらず、上記の内訳は実際に発生した請求額の近似です。
